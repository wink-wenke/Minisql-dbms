# MiniSQL 数据库管理系统 — 实训编写流程得分要点

> 《大型平台软件设计实习》课程配套评分指南
>
> **项目本质**：综合编译原理、操作系统、数据库三门课程，构建完整数据库管理系统。
> 评分围绕三大模块展开：SQL编译器 × 存储系统 × 数据库引擎

---

## 一、评分总览

### 1.1 验收五大目标

| 目标 | 核心要求 |
|------|---------|
| **正确** | 合法SQL通过完整流水线（编译器→引擎→存储），得到正确结果 |
| **稳健** | 非法输入不崩溃，能区分词法/语法/语义/执行错误并精确定位 |
| **可扩展** | 三大模块具有清晰边界，文法、AST、Catalog、Plan、Page节点可独立扩展 |
| **可优化** | 至少实现若干规则式优化，并能展示优化前后差异 |
| **可验证** | 有系统测试、边界测试、教师隐藏测试结果，通过率可量化 |

### 1.2 三模块并重原则

**本项目不是只做编译器**。评分权重分布在三大模块：

```
┌─────────────────────────────────────────────────────────┐
│           SQL编译器（编译原理）                           │
│  词法分析 → 语法分析 → 语义分析 → 执行计划生成 → 优化     │
├─────────────────────────────────────────────────────────┤
│           数据库引擎（数据库）                            │
│  执行算子 → 存储引擎 → 系统目录                          │
├─────────────────────────────────────────────────────────┤
│           存储系统（操作系统）                            │
│  页式存储 → 缓冲池 → 磁盘I/O                            │
└─────────────────────────────────────────────────────────┘
  三者缺一不可，任何一个模块缺失都会严重影响得分
```

### 1.3 任务分层

```
┌─────────────────────────────────────────────────────────┐
│  Extension（扩展）— 体现区分度                            │
│  编译器：JOIN/GROUP BY/Fuzz/EXPLAIN                      │
│  引擎：  事务/并发控制/索引扫描/访问控制                   │
│  存储：  日志恢复/B+树/MVCC/代价模型                      │
├─────────────────────────────────────────────────────────┤
│  Advanced（进阶）— 冲高分的关键                           │
│  编译器：AND/OR/NOT + 2+优化规则 + 隐藏测试高通过率        │
│  引擎：  算子扩展 + Catalog持久化                         │
│  存储：  锁与闩锁 + 脏页刷回 + 性能日志                   │
├─────────────────────────────────────────────────────────┤
│  Core（基础必做）— 不做则扣分                             │
│  编译器：Lexer + 四类SQL + AST + Catalog + Plan + 错误定位│
│  引擎：  CreateTable/Insert/SeqScan/Filter/Project       │
│  存储：  页式存储 + 缓冲池 + 表文件 + 读写测试             │
└─────────────────────────────────────────────────────────┘
```

## 二、模块一：SQL编译器得分要点（编译原理）

### 2.1 基础必做项

| 得分项 | 具体要求 | 扣分风险 |
|--------|---------|---------|
| Token类型完整 | KEYWORD/IDENTIFIER/CONST/OPERATOR/DELIMITER五类 | 缺少类型直接扣分 |
| 位置信息保留 | 每个Token携带`<Line, Column>` | 无位置则后续错误定位无法实现 |
| 大小写处理 | 关键字大小写不敏感 | 未处理则通过率下降 |
| 字符串处理 | 单引号字符串，处理转义`''` | 未处理则边界测试失败 |
| 注释跳过 | `--`单行和`/* */`多行注释 | 未处理则合法SQL被误判 |
| 非法输入处理 | 返回错误类型+位置+原因，不得崩溃 | 直接崩溃=严重扣分 |
| 四类SQL | CREATE/INSERT/SELECT/DELETE完整支持 | 缺少任一类扣分 |
| AST构建 | Statement+Expression节点分离，体现优先级 | Token堆叠=扣分 |
| Catalog | createTable/findTable/findColumn/getType | 缺少则语义分析无法进行 |
| 语义检查 | 表/列存在性、类型一致性、INSERT匹配 | 缺少则通过率大幅下降 |
| Logical Plan | CreateTable/Insert/SeqScan/Filter/Project | 缺少则无法驱动执行引擎 |
| 错误定位 | 行号+列号+原因，区分词法/语法/语义阶段 | 无法定位=扣分 |

**关键验证SQL**：
```sql
-- 注释 + 大小写 + 多字符运算符
-- query
sElEcT name FROM student WHERE age >= 18 AND name != 'Tom';

-- 字符串转义
INSERT INTO t VALUES ('Tom''s book');

-- 优先级验证
SELECT * FROM t WHERE a = 1 OR b = 2 AND c = 3;
```

### 2.2 进阶项

| 得分项 | 具体要求 |
|--------|---------|
| AND/OR/NOT | 完整支持，体现优先级（NOT > 比较 > AND > OR） |
| 2+优化规则 | 常量折叠、布尔化简、Projection Pruning等 |
| 错误诊断增强 | 语法错误给出期望集合，语义错误区分多种类型 |
| 隐藏测试高通过率 | 学生自建+教师隐藏测试，通过率=重要验收依据 |
| Plan可视化 | 树形/缩进/图形方式展示Logical Plan |

### 2.3 扩展项

| 功能 | 难度 |
|------|------|
| UPDATE / ORDER BY / GROUP BY / JOIN | 中-高 |
| Fuzz Testing（随机SQL生成+变异） | 中 |
| EXPLAIN命令 | 中 |
| 高级错误恢复 | 高 |

## 三、模块二：存储系统得分要点（操作系统）

> 体现操作系统课程知识的直接应用：内存管理、页式存储、缓冲池调度

### 3.1 基础要求（必须完成）

| 得分项 | 具体要求 | 验收标准 |
|--------|---------|---------|
| **页式存储模型** | 实现页的分配、释放、读写 | 能正确分配新页并读写数据 |
| **表文件与元数据** | 表文件的创建、打开、关闭；元数据持久化 | 表创建后能正确读取列定义 |
| **缓冲池与替换策略** | 实现LRU或FIFO替换策略；支持Pin/Unpin机制 | 命中率统计正确，替换逻辑无Bug |
| **正确读写与测试** | 数据写入后能正确读回；有基本读写测试 | 端到端读写测试通过 |

### 3.2 深化要求（显著提分）

| 得分项 | 具体要求 | 验收标准 |
|--------|---------|---------|
| **并发访问的锁与闩锁** | 共享锁/排他锁；Latch保护缓冲池并发访问 | 多线程读写不出现数据竞争 |
| **脏页刷回与故障检查** | 脏页在淘汰或检查点时写回磁盘；异常退出后数据不丢失 | 模拟故障后数据可恢复 |
| **任务队列和资源限制** | 缓冲池大小有限时的等待机制；页请求排队处理 | 资源耗尽时优雅等待而非崩溃 |
| **性能基准与诊断日志** | 命中率、I/O次数、替换次数等关键指标 | 能输出性能统计报告 |

### 3.3 拓展方向（体现区分度）

| 得分项 | 具体要求 | 难度 |
|--------|---------|------|
| **日志与恢复** | WAL（Write-Ahead Logging）；Undo/Redo恢复 | 高 |
| **B+树或索引** | B+树索引结构；基于索引的快速查询 | 高 |
| **多版本并发控制（MVCC）** | 多版本记录；读写不阻塞 | 高 |
| **代价模型与查询优化** | 基于统计信息的代价估算；选择最优执行计划 | 高 |

### 3.4 存储系统得分速查

```
必须完成（否则严重扣分）：
  ✅ 页式存储模型（分配/释放/读写）
  ✅ 表文件与元数据持久化
  ✅ 缓冲池 + LRU/FIFO替换策略
  ✅ 正确读写测试

尽量完成（显著提分）：
  ⭐ 并发访问锁机制
  ⭐ 脏页刷回与故障恢复
  ⭐ 性能基准与诊断日志
  ⭐ 任务队列与资源限制

锦上添花（体现区分度）：
  💎 日志与恢复（WAL）
  💎 B+树索引
  💎 MVCC
  💎 代价模型与查询优化
```

## 六、工程化开发与系统集成得分要点

> 本项目采用"接口先行、Mock解耦、增量集成"的工程化开发模式。
> 三人按模块分工，代码并行开发，通过预定义接口和Mock对象消除依赖，最终多次增量集成形成完整DBMS。

### 6.1 接口先行得分要点

| 得分项 | 具体要求 | 评分标准 |
|--------|---------|---------|
| **接口文档完整性** | 三模块之间的接口契约必须提前定义并文档化 | 有完整接口文档=满分；接口模糊=扣分 |
| **共享数据结构** | LogicalPlan/Record/RID/TableSchema等数据结构三模块共用 | 三模块使用统一定义=满分；各自定义=扣分 |
| **接口一致性** | 代码实现与接口文档一致 | 完全一致=满分；有偏差=扣分 |

**必须定义的接口**：
- 编译器对外接口：`compile(sql) → LogicalPlan`
- 引擎对外接口：`execute(plan) → QueryResult`
- 存储对外接口：`scanTable/insertRecord/createTable` 等

### 6.2 Mock解耦得分要点

| 得分项 | 具体要求 | 评分标准 |
|--------|---------|---------|
| **Mock实现** | 每个模块都有Mock替代依赖模块 | 有Mock且可独立运行=满分 |
| **独立测试** | 各模块使用Mock能独立通过测试 | 独立测试全通过=满分 |
| **Mock覆盖度** | Mock能覆盖依赖模块的核心接口 | 核心接口全覆盖=满分 |

### 6.3 增量集成得分要点

**集成不是一次性完成的，而是分阶段替换Mock**：

| 集成阶段 | 验证内容 | 得分要求 |
|---------|---------|---------|
| **阶段1→2**：编译器+引擎 | Plan能被引擎正确消费 | Plan结构匹配、节点类型正确 |
| **阶段2→3**：引擎+存储 | 算子能正确调用存储接口 | scanTable返回正确记录、insertRecord写入成功 |
| **阶段3→4**：全链路 | 三模块全部真实连接 | CREATE→INSERT→SELECT→DELETE端到端通过 |

**集成质量评分**：
| 得分项 | 评分标准 |
|--------|---------|
| 每次集成都有验证 | 每阶段有测试用例验证=满分；无验证直接拼接=扣分 |
| 集成问题可定位 | 能快速定位集成Bug属于哪个模块=满分 |
| 接口变更同步 | 接口变更后Mock同步更新=满分；不同步=扣分 |

### 6.4 端到端数据流验证

必须能展示从SQL文本到最终结果的完整链路：

```sql
-- 完整演示SQL
CREATE TABLE student(id INT, name VARCHAR, age INT);
INSERT INTO student(id, name, age) VALUES (1, 'Alice', 20);
INSERT INTO student(id, name, age) VALUES (2, 'Bob', 19);
SELECT name FROM student WHERE age > 18 AND id != 3;
DELETE FROM student WHERE id = 1;
```

**展示内容**：
1. Token流输出（编译器→Lexer）
2. AST结构（编译器→Parser）
3. 语义检查结果（编译器→Semantic）
4. Logical Plan（编译器→Plan Generator）
5. 优化前后对比（编译器→Optimizer）
6. 执行结果（引擎→Executor调用存储系统）

### 6.5 模块间接口清晰度

| 检查项 | 要求 |
|--------|------|
| 编译器→引擎 | Logical Plan接口明确，引擎能直接消费 |
| 引擎→存储 | scanTable/insertRecord接口明确，引擎通过接口访问存储 |
| Catalog双重角色 | 编译器侧（符号表）和引擎侧（系统目录）的数据一致性 |
| 错误传播 | 各阶段错误能正确向上传递，包含位置信息 |

### 6.6 团队协作规范

| 得分项 | 具体要求 | 评分标准 |
|--------|---------|---------|
| **分工明确** | 三人各负责一个模块，职责清晰 | 有明确分工记录=满分 |
| **接口变更管理** | 接口变更三方确认后同步更新 | 有变更记录=满分；随意改接口=扣分 |
| **集成节奏** | 按计划分阶段集成，而非最后一次性拼接 | 有集成计划且执行=满分 |

## 九、现场验收注意事项（高权重）

> 现场验收比"看代码"更能区分真实能力

### 9.1 随机代码讲解

教师随机点名函数（如`parseExpression`、`bufferPool.getPage`、`seqScan.next`），学生需现场解释：
- 函数的输入输出
- 核心算法逻辑
- 与其他模块的交互

**准备建议**：对三大模块的核心函数都能画出流程图。

### 9.2 需求修改

现场增加小需求（如`<=`、`NOT`、`DISTINCT`、新的页替换策略），可使用大模型辅助，但必须完成集成。

**关键**：展示"驾驭代码"的能力，而非"手敲所有代码"。

### 9.3 现场Debug

给出失败场景，让学生定位属于哪个模块/阶段：
- 编译器：Token识别错误 / 文法不匹配 / 类型检查失败
- 引擎：算子执行错误 / Catalog不一致
- 存储：缓冲池替换Bug / 页读写错误 / 脏页未刷回

### 9.4 AST / Plan 推导

给一条新SQL，现场画出：
- 关键AST结构
- Logical Plan树
- 执行过程中各模块的交互

## 十、报告撰写要点

### 10.1 关键设计决策

- 三模块为什么这样划分边界？
- 为什么选择递归下降 / LL(1)表驱动？
- 缓冲池为什么选择LRU / FIFO？
- Catalog如何在编译器侧和引擎侧保持一致？

### 10.2 问题定位过程

- 遇到了哪些Bug？
- 如何定位到具体模块/阶段？
- 修复方案是什么？

### 10.3 AI辅助使用说明

**必须如实说明**：
- 哪些部分使用了AI辅助（如代码骨架、单元测试、Debug）
- 哪些部分是自己设计的（如文法、AST定义、页结构、替换策略）
- 如何验证和修改AI生成的代码

**不能通过验收的情况**：
- 代码能跑但讲不清
- 改一个需求就失效
- 隐藏测试大量失败
- 不知道错误属于哪个模块/阶段
- 无法解释AI生成的模块

### 10.4 端到端演示

附一条完整的端到端演示SQL，展示三大模块的协作：
1. SQL文本 → Token流（编译器Lexer）
2. Token流 → AST（编译器Parser）
3. AST → 语义检查 → Logical Plan（编译器）
4. Logical Plan → 执行算子调用（引擎）
5. 执行算子 → 读写数据页（存储系统）
6. 结果返回
